# Interactive Refinement

Use this workflow for a concrete feature or defect with an owner available to perform manual tests. It coordinates refinement; the active `delegation-orchestrator` skill owns admission, dispatch, contracts and independent acceptance. Follow that skill's actual native tools for the selected profile. In the global profile, the parent uses `harness_orchestration` and `subagent`; slash commands are user-facing intake. Project-specific refinement skills may add domain criteria without replacing the shared protocol. The active roles are `researcher`, `planner`, `implementer`, and `validator`.

1. Before implementation, establish a measurable goal, observable success criteria, manual test environment, finite positive maximum rounds, and applicable agent/attempt budget. Reuse an existing matching owner agreement and standing authorization; do not ask for routine approval again. Ask only for missing decisions or authorization that the requested next action actually requires. A closed round needs a fresh finite scope and budget; derive them from the owner's current instruction when supplied. Record the agreement and next safe action using the active profile's template. In the global profile use `.opencode/bootstrap/memory/templates/interactive-refinement-test-plan.md` beneath the immutable runtimeRoot returned by admission; preserve project-owned plan locations and history. Legacy profiles may use their seeded `.memory/templates/interactive-refinement-test-plan.md`.
2. Default to serial rounds and serial role work. Request fresh scoped tasks through the active delegation protocol for planning, implementation and independent validation as needed; do not invent parallel capacity or reuse a completed task thread. The orchestrator enforces its dispatch, trace and budget rules. Keep a bounded change scope and link the round's implementation and automation evidence. Before choosing an edit, identify evidence that distinguishes competing causes, compare the automated fixture with the owner's actual runtime, and resolve prerequisite behavior before tuning dependent behavior. Prefer bounded live telemetry and negative controls when fixture results disagree with actual use; record the limits of each observation.
3. For each round, have a planner revise the versioned manual tasks for unresolved risks and prior feedback. Retain earlier round records and task results unchanged, identify added/changed/retired tasks, and keep stable task IDs for tasks reused without changing their meaning. The implementer makes scoped changes and runs relevant automation; an independent validator checks the changed behavior and automation on the resulting tree before code acceptance. A passing automation check never stands in for a manual owner verdict.
4. Give the owner ordered manual steps and expected observable results. Record actual observations, questions and owner feedback only when supplied; until then mark them pending. The owner reports `success`, `needs-work`, or `blocked` (or leaves `pending` while undecided). An owner success verdict is not independent validator proof. When automation passes but actual use fails, record the manual criterion as failed and investigate the earliest unmeasured runtime divergence. Keep source review, build, automation, live evidence, owner testing and formal gate acceptance distinct. Decide whether the measurable goal is met, a new PRD goal is needed where applicable, or a budgeted next round addresses the remaining issues.
5. Stop without claiming success on a failed validation gate, missing owner decision, blocker, exhausted round/agent budget, or unsafe interruption. State the blocker or next safe action; never retry indefinitely or imply a live provider or deployment check occurred without evidence.

The Markdown template is a human-maintained plan. Resolve `.opencode/schemas/interactive-refinement-test-plan.schema.json` against the active immutable runtimeRoot in global mode. It describes an optional structured JSON record with corresponding concepts; it does not validate Markdown or replace owner sign-off. Use the template's field correspondence when recording both formats. After installing or changing this skill, restart OpenCode to load it.
