# OpenCode Harness Instructions

This project is the source and release-QA repository for a standalone OpenCode harness projection. Its source surface is inventoried by `.opencode/harness.manifest.json` and includes source-only roots, optional assets, and release tooling.

The root npm package is the versioned Linux/Node-24 external runtime. `node bin/opencode-harness.mjs prepare` probes the selected trusted OpenCode executable and creates or verifies an owner-only mutable cache separated by its reported version; `run --workspace /absolute/git/root` launches the selected OpenCode without a version allowlist without copying `.opencode` into that workspace. Runtime assets, workspace work, and traces are separated by launcher-set roots. External endpoint catalog/profile inputs are all-or-none, advisory, and force-local false. No provider credential or global config mutation belongs to the runtime. The explicit V2-only `--v2-auth-data-home` opt-in may read-only snapshot an owner-only native auth database outside the runtime, export exactly one active OpenAI OAuth connection inside a network-isolated Bubblewrap process, import that connection into the independently absent per-launch database after the V2 guard probe, remove the source snapshot before the requested client, and remove the launch database after exit; never mutate the operator source or retain credential bytes in runtime assets or traces.

Runtime verification is a closed recursive inventory: managed leaves are 0644, intermediate directories are 0700, typed generated files are owner-only, and `node_modules` is the sole recursive generated subtree. Every symlink remains forbidden except an immediate `node_modules/.bin/<safe-name>` link whose current-user-owned relative target is stable, has no symlinked component, stays inside the same `node_modules`, ends at an owner-controlled non-group/world-writable regular file, and exactly matches installed package `bin` metadata plus the outer package/lock versions and an exact `@opencode-ai/plugin` root relationship matching its lockfile and installed package version. Runtime acceptance is dependency-free and requires no network or reference installation; metadata agreement is structural validation, not package-byte authentication. External provider/catalog/profile bytes are no-follow-read, validated, copied to owner-only per-launch snapshots outside the runtime, passed to one child, and removed afterward. Each credential-free projected model must contain exactly its matching `name` and positive integer `limit.context`/`limit.output` metadata, with `limit.output < limit.context`; validation occurs before snapshot and no limit is defaulted. Project JSON and the supported JSONC subset (line/block comments plus trailing commas) are parsed fail-closed for collisions; project plugins require explicit acknowledgment and remain unsandboxed. Executable probing and launch use one resolved absolute path. These controls target accidental changes and other UIDs, not malicious same-UID replacement, registry compromise, or a compromised package artifact.

Ambient `OPENCODE_DB` is rejected. By default, every child receives unique, independently absent database, WAL, and SHM paths inside its owner-only launch snapshot; `XDG_DATA_HOME` passes through unchanged, and only owner-mode-0600 companions are accepted. Cleanup uses canonical path and device/inode identities captured for both snapshots parent and launch directory. Before any post-child inventory or `readdir`, it rechecks parent/launch identity, owner/mode, immediate-child containment, and root exclusions; after quarantine it requires unchanged parent and matching quarantine device/inode before recursive no-follow unlink. Successful cleanup revalidates parent identity and quarantine absence. Any cleanup failure preserves the original child/inventory rejection first and reports an exact absolute retained launch path before rename or quarantine path after rename; identity/containment mismatch causes no deletion. Node's lack of descriptor-relative recursive unlink leaves same-UID path replacement within the documented race limitation.

With the owner's explicit matching authorization, V2 `run --native-session-db ABS` may bind an existing native OpenCode database outside workspace/runtime/trace roots after canonical-path, current-user ownership, mode-0600, and single-link checks of the database and its companions. This changes the native session/auth database, which the launcher never deletes. The activation guard and fresh-ID managed workflow policy remain required; old session visibility never makes a prior managed Task resumable.

All cache/state/trace/snapshot/workspace roots must be absolute lexical-canonical paths with no dot, dot-dot, duplicate/trailing separator, NUL, or intermediate symlink. Missing suffixes are created one component at a time only below a verified current-user mode-0700 directory. A root-owned sticky directory such as `/tmp` is usable only through an already-existing current-user mode-0700 immediate child; the launcher never creates that child. Group/world-writable worktrees and project config/plugin/skill surfaces are unsupported, and project security surfaces are rechecked after the version probe immediately before spawn. Custom `skills.paths` entries must be absolute trusted roots and are recursively checked for `delegation-orchestrator/SKILL.md`.

The stopped-run recovery shell has a separate, narrow fallback when no existing private state parent is available: its plugin may create only its own mode-0700 recovery directory immediately under the current user's canonical home directory, provided that home and every ancestor have no symlink and home is not group/world writable. This exception does not apply to launcher cache, state, trace, snapshot or workspace roots.

PATH fallback locates the first executable `opencode` candidate in standard PATH order, then validates that selected entry and its resolved ancestry; unrelated later PATH entries are not inspected. An unsafe selected candidate fails rather than silently falling through to another. `OPENCODE_BIN` is explicit operator selection, but it remains subject to canonical-path, resolved-ancestry, owner, mode, version, and post-probe byte-identity checks; it is not a security bypass. Current-user mutation between the final check and exec remains within the documented same-UID limitation.

Project and custom-skill security fingerprints stream file content through fixed-size buffers with before/after descriptor identity checks. The 1 MiB parser bound applies only to JSON/JSONC and external structured inputs, not ordinary OpenCode-loadable skill/plugin/agent/command assets.

The installable `portable-core` profile is a narrower boundary defined only by `.opencode/portable.manifest.json`. Bootstrap does not copy or require destination `AGENTS.md`, `opencode-harness.design.md`, `opencode.json`, root `.gitignore`, source reference inventory, deployments, optional workflows/meta-skills, or orchestration history. Those source files may document and test the portable profile, but installed portable runtime and validation must not depend on them.

`.agents/` and `.codex/` are reference-only prior projection examples. They may inform wording or compatibility checks, but OpenCode commands, agents, workflows, manifests, plugins, scripts, and runtime guidance must not depend on those paths.

## Harness Conventions

`run` infers the Git worktree root when `--workspace` is omitted and selects the validated source TUI profile automatically for this exact source checkout. On V2, both source and external runtime terminal profiles may use an explicitly selected native session database, preserving native provider authentication and session history without restoring managed Task authorization. A user-owned `opencode` shell entry point may route all Git repositories through `run`; package installation does not silently replace the native command.

An installed `portable-core` project on Linux V2 uses its own validated plugin entry and V2 module closure through `run`; the launcher must prove the exact active native guard before attaching a client. Project-owned optional skills and existing memory guidance remain untouched. A damaged portable profile or colliding project plugin/configuration fails closed; it must never fall back to a second external guard.

- Use delegation-only parent behavior when `delegation-orchestrator` or `/delegate-orchestration` is invoked; outside that invocation, normal project instructions apply.
- Preserve exactly four active role names: `researcher`, `planner`, `implementer`, and `validator`. Specialties are explicit bounded task modes: planner `plan|synthesis`, implementer `implementation|integration`, and validator `validation|review|artifact-proof|integration-check`.
- `.opencode/skills/delegation-orchestrator/SKILL.md` is the sole protocol authority. `/delegate-orchestration` is a thin natural-language intake wrapper. The parent assembles and validates the internal orchestration specification, then delegates and synthesizes only; leaf agents deny further delegation and the orchestrator skill.
- Keep role agents under `.opencode/agents/` as Markdown files with `description`, `mode: subagent`, and conservative `permission` frontmatter.
- Keep role-specific command prompts under `.opencode/commands/` with `description` and `agent` frontmatter only; do not set `model` in command files. The central `/delegate-orchestration` command is the exception: it omits `agent` and sets `subtask: false`.
- Keep the committed neutral routing default in `.opencode/routing/harness-model-routing.example.json`; local routing is disabled with no catalog or selectors. `.opencode/routing/harness-model-routing.local.example.json` is an explicit opt-in example/test fixture and is never an implicit default. An operator may create the ignored `.opencode/routing/harness-model-routing.json` override. Implicit loads choose a present custom file first, otherwise the neutral example, never merge, and fail rather than falling back when a present custom file is unreadable, malformed, or invalid. Explicit config paths are exact. If both implicit files are absent, restore/copy the neutral example. Routing fixtures do not configure native provider transport, and force-local remains false by default.
- Use `.memory/protocols/memory-management.md` for project-owned memory. Store static references/templates under `.memory/` and generated orchestration memory under `.memory/orchestrations/<orchestration-id>/`.
- Require every delegated role to follow `.opencode/contracts/role-io-contracts.json`, shape trace artifacts according to `.opencode/schemas/memory-trace-artifact.schema.json`, and write or reference `.memory/orchestrations/<orchestration-id>/roles/<role>/<artifact-id>.md`.
- Give every separately scoped delegated task a new `delegationTaskId` and fresh child thread; fresh Task calls omit `task_id`. Reuse is allowed once to answer a child-originated clarification while that exact task remains unresolved, or for bounded context-only updates to an active background worker under the authoritative protocol. Retry, remediation, correction, follow-up, changed scope/role/deliverable, and terminal work always start fresh child threads; direct unverified child-dispatch surfaces are prohibited for managed orchestration.
- When the managed process guard stops, any primary session may use read-only recovery status and read/grep/glob/list for diagnosis; only the exact bound parent may use resolve/release. Resolve may retry native abort after a correlated launch and must prove idle status and parent identity; a pending Task callback cannot be replaced with an idle observation. Release requires proven native termination, unchanged marker/spec, in-scope workspace effects and a reviewed exact tree hash; it permits only a fresh orchestration ID, never a resumed child or old gate. If proof cannot be obtained in-session, keep the old guard and marker retained. An authenticated primary may continue in the same OpenCode session using the recovery shell: Bubblewrap gives it a persistent owner-only external work directory as the sole writable bind, with the old workspace, trace and host read-only and network isolated. It may prepare and work on a reviewed source copy there; never treat old effects as accepted or run a new managed Task until native proof permits release.
- V2 primary sessions may request exact owner-approved HTTPS download, inert archive install and offline recovery build through `harness_external_artifact_download`, `harness_external_archive_install` and `harness_external_recovery_build`. Every stopped-run V2 shell command also requires a separate exact native approval. During an unresolved run, all action writes remain in the isolated recovery directory. Each action requests the full source, integrity, destination, writes, script policy and limits applicable to it; none is a managed acceptance gate.
- Treat `.opencode/plugins/index.js` as the only auto-loaded local plugin entry point. Keep segmented guardrail/telemetry modules under `.opencode/plugin-modules/`, such as `.opencode/plugin-modules/harness-lifecycle.js`, so OpenCode does not auto-load them separately. Do not add local plugin file paths to `opencode.json`.
- Default local-model DAG execution to serial unless explicit authorization or distinct-capacity evidence permits parallelism. Default remediation to one cycle per scoped work unit and enforce declared loop/agent budgets.
- Treat lifecycle hooks and progress artifacts as guardrails or coordination evidence only. Independent validator evidence is required, and findings block only with command-backed evidence tied to the goal, an acceptance gate, or changed behavior.

## Delegation Boundaries

Parent orchestration may extract user intent, ask focused intake questions, generate mechanical identifiers and conservative policy defaults, derive bounded coordination structure, validate the normalized internal orchestration specification, classify work, create delegation packets, pass context, review returned evidence, request bounded remediation, and synthesize final summaries. It must not conduct substantive research, draft implementation plans, edit or integrate files, or validate acceptance in place of leaf evidence.

When caller-supplied routing metadata is present, preserve these labels exactly: `### Delegation Parameters`, `**Provider Model**`, `**Routing Config**`, `routingServiceUrl`, `localModelEnabled`, `preferLocal`, and `localModelFallback`. When the original request does not include enriched routing metadata, do not invent values.

## Validation

For this source repository, run `node .opencode/scripts/validate-harness.mts` and task-specific checks. Source QA requires the source roots, static reference inventory, and indexed orchestration history; it validates only committed routing fixtures and never consumes the private custom override. It also invokes the installed-profile-equivalent portable validator.

For a bootstrapped installation, run `node .opencode/scripts/validate-portable-harness.mjs --root .`. Portable acceptance requires only portable-manifest managed files and minimal seeded memory, not this file or other source-only roots/history.

For package/runtime changes also run both runtime test scripts and `npm pack --dry-run --json`. Fixture launch uses only a fake exact-version OpenCode binary in owner-controlled temporary roots. Real activation, provider health, auth, network, global installation, and publication require separate authorization. Quit and restart OpenCode after runtime/config/plugin changes. Roll back by invoking the prior package version; caches are version-separated and retained.

Validation uses the committed routing example explicitly so an optional private override cannot change acceptance. After changing either routing file or plugin code, fully quit and restart OpenCode; running sessions retain loaded configuration.

## Global native profile

The separate `global-native` profile uses `global prepare|install|doctor|rollback|uninstall` and explicit exact-entry project migration/restoration. Its authoritative closure is `.opencode/global.manifest.json`, with profile-specific delegation guidance under `.opencode/global/skills/delegation-orchestrator/`. It keeps native ordinary tools/permissions and applies protocol admission/result rejection locally. Read `docs/global-profile.md` for capability limits and migration. The launcher/stop/recovery invariants elsewhere in this file govern legacy source/portable/external profiles; do not introduce them into the global adapter import closure. For global changes run `npm run validate:global` and `npm run test:global` as well as all existing source/runtime checks. No real global installation or provider activation is implicit in a code change.
