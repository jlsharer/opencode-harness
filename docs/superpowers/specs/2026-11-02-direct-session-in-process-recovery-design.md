# Direct session in-process recovery design

Date: 2026-11-02. Design-only follow-on to the completed [production design](2026-11-02-direct-session-production-design.md) and [execution record](../plans/2026-11-02-direct-session-production.md). Baseline: `76b9f24`, branch `codex/shared-workflow-refactor`.

The owner requested continuation of the existing implement/review/commit-and-push work in this checkout using fresh agents. The recommendation, narrow reason allowlist, observation bound and interfaces below are author choices under that continuation, not separately expressed owner requirements. A fresh independent builder consistency check found nothing important left to resolve. Owner design approval and an implementation plan are the next gates; this document records no implementation or live acceptance.

## Intent and approaches

Allow the exact bound parent to retire an uncertain foreground direct implementation after its original operations and owned callbacks actually finish, review its effects, and start a completely new orchestration. Stopping must permanently revoke old result acceptance. Native idle alone must never release an outstanding operation or callback.

Three approaches were considered:

1. **Retained in-process proof (recommended for this increment).** Reuse the existing recovery tools, with a separate private direct-session proof branch in the same plugin instance. Its operation/callback ledger and privately owned lease remain available. This addresses delayed settlement without inventing crash recovery.
2. **Durable already-settled certificate (later).** Persist only settlement already established by intact in-memory evidence, with a versioned crash-safe publication/retirement protocol. This could cover reload after certificate publication, but cannot cover a crash before proof. It adds filesystem and crash-boundary work outside this increment.
3. **General recovery after losing execution evidence (unsupported).** Public plugin APIs supply neither an all-operation fence nor reconstruction of lost callback accounting. Native restart can resume claims; deleting a child or seeing it idle does not fence a late create/prompt. No proposed implementation can safely release arbitrary old version-1 leases on this basis.

The parent selected the first approach as the bounded next increment. This design keeps default-off Linux V2 fresh foreground `implementer/implementation` as the only direct route. It adds no validator route, durable journal, payload compaction, new lifetime limit, package dependency, native core patch, generic release endpoint, or live activation. The existing Job recovery path retains its behavior and evidence requirements.

## Existing facts and native authority

The production transport owns a pending-Promise set, but invokes API functions before registering their returned Promises, reconciles a snapshot for at most 2,000 ms, and erases error provenance in a generic catch. Its late-create interrupt is useful but insufficient. Adapter `directCalls.after` means a branch was entered, including correlation failure; it does not prove a correlated callback finished. Managed `directRecord` correctly rejects stopped/deadline-expired handles and must continue doing so for acceptance. `interrupt()` moves live controller attempts to `cancel-requested`; repeated generic interruption currently sets `recoveryFault`. Direct finalization also sets `used` on failure. None of those acceptance-oriented flags is a recovery receipt.

Native assumptions are grounded in committed blobs at `68bc26b7da1990ce10ffecfbc1e09eb13aa5d824` in `/home/joshl/.cache/opencode-harness/v2-native-api-src`. Its dirty working tree is not evidence. Relevant seams are `packages/plugin/src/promise/{adapter,tool,session}.ts`, `packages/core/src/tool.ts`, `packages/core/src/session/{session,execution,run-coordinator}.ts`, `packages/core/src/session/execution/restart.ts` and the consumed session/message schemas.

- `interrupt({sessionID,resume:false})` acknowledgment precedes asynchronous cleanup. `wait` awaits execution idle, including drain finalizers and successor rechecks. Use both, after original submissions have settled.
- Prompt admission/wake can continue after an earlier interrupt. A visible prompt or idle child does not prove an outstanding prompt Promise ended.
- Native tool execution catches typed `Tool.Error`, emits an error after-event, and returns that error after the hook. Native interruption can bypass that branch; an after-callback is not guaranteed.
- The Promise adapter wraps the exact rejected executor error as `Tool.Error.error` (unless already a native Tool.Error). This permits a private object-identity check in the same instance. The committed-source audit and an adapter-faithful fixture must prove this seam before implementation acceptance; error text is never authority.
- The public Promise session domain has the six APIs already projected by production: create, prompt, interrupt, wait, get, context. It exposes no inbox-cancel/tombstone, server epoch, or all-plugin hook fence.

## Supported stop causes and permanent disqualifiers

The initial typed allowlist has exactly two origins:

| Private stop code | Trusted origin | Conditions retained |
| --- | --- | --- |
| `deadline-expired` | The already-admitted fixed task deadline is reached by its timer/check | Deadline value never changes; elapsed time never proves settlement |
| `caller-cancelled` | The exact originally captured caller AbortSignal fires/is observed aborted | The signal reference and exact call tuple still match; missing native after remains blocked |

Introduce typed stop provenance at the actual originating branches. Human diagnostics remain strings; string matching, generic catch reclassification and caller-supplied enums/booleans cannot create eligibility. A first allowlisted stop does not excuse a later independent fault. Expected propagation of the *same private stop token* through execute catch, transport stop and final after rejection is idempotent, not a new recovery fault. Unknown catches remain disqualifying. All native operation rejections, unexpected synchronous throws, malformed native results, native failure outside the two origins, unsupported task result, artifact/security failure and finalization failure are excluded from this first increment. This conservatism leaves some provably retireable errors for later work.

The following are sticky for the owned attempt: event subscription loss even if subsequently reconnected; unload/dispose; activation/role/permission authority loss; duplicate/mismatched callback or operation identity; uncorrelated or additional child-created event; foreign prompt, steering or switch activity; unsafe/out-of-scope effects or artifact paths; changed spec/start marker/root/lease; a callback proof-processing error; rejected/unknown native operation; or any unclassified stop reason. Observing a later clean snapshot never erases one. Pending operations/callbacks are blockers that can settle; a callback that never arrives is not invented or decremented. Duplicate after-events are sticky even if the first one settled.

For the smallest supported tranche, require create and prompt to have been invoked and eventually fulfilled with matching acknowledgments, and require the exact own prompt to be promoted into child context. No-create/no-prompt, failed create/prompt, queued/unobserved prompt and missing-child cases remain blocked. A cancellation that skips native after is intentionally unrecoverable here.

## Private transport contract

Keep the implementation in `direct-session-transport.ts`. The following names are proposed concrete interfaces, not claims that they already exist. They are available only to trusted local code, never tools or packet JSON:

- `DirectAttemptHandle`: frozen opaque object backed by a transport-owned WeakMap. Created/registered before the first create invocation; bound to the branded admission, exact caller tuple and signal reference, child/prompt IDs, immutable original deadline and plugin-instance identity. A prepared handle lets the adapter register managed recovery before native reentrancy. `execute(handle)` continues to produce only `DirectCandidate` on normal success.
- `inspectSettlement(handle)`: bounded diagnostic projection containing stop phase, pending counts by operation name, create/prompt acknowledgment presence, and bounded disqualifier codes. It never exports the actual ledger, receipt, raw prompt/result, or a release/acceptance boolean.
- `stop(handle, privateCause)`: permanently closes acceptance and is idempotent for the same cause. Publish stopped state before calling callbacks/native APIs. Schedule at most the initial stop interrupt plus one late-create interrupt if needed; every interrupt is tracked. Repeated wrapper/after stop propagation must not spawn an unbounded interrupt loop.
- `reconcileStopped(handle)`: serialized, bounded, private native termination observation. Returns an opaque `DirectTerminationReceipt` only after the sequence below; it never calls `consumeCandidate` or restores acceptance. A pending reconciliation blocks another, including after its observation timeout until the native operation actually settles.
- `assertTermination(receipt, handle)` and `consumeTermination(receipt, handle)`: synchronous WeakMap identity/generation validation and one-use retirement. A receipt is bound to one handle and one completed observation generation; replacing a receipt invalidates the previous one. The managed layer owns the independent callback/authority generation and must check it alongside this token. Copying an object or supplying an integer cannot manufacture either fact.

Replace `track(api.method(...))` with a thunk-based named operation wrapper. Before invoking any native API or owned asynchronous callback, publish an operation entry (`create`, `prompt`, `wait`, `get`, `context`, `interrupt`, `child-acknowledgment`) and increment a monotonic operation generation. Record invocation identity, phase (`invoking|pending|fulfilled|rejected`), and bounded outcome classification. Synchronous reentrancy sees `invoking`; synchronous throws settle as rejected. Use trusted Promise assimilation and explicit completion handlers; no time-based deletion. Validate create/prompt acknowledgments inside their tracked settlement handlers even when the ordinary stage already lost its cancellation race. Track late continuation handlers through their own completion, so a settled create cannot be momentarily counted as drained before its late interrupt is registered.

The stopped executor may return after the existing 2,000 ms best-effort reconciliation window, but retained operations continue being tracked dynamically. That window does not grant recovery. Original execute continuation settlement, native operations and adapter settlement are distinct facts. Candidate consumption permanently fails after stop, including a previously staged candidate.

## Adapter and managed callback lifecycle

`v2-native-plugin.ts` owns the before-event/executor/parent-after record; `managed-dispatch.ts` owns child-tool and command observations. Register one private recovery capability for the exact managed handle before create can fire. Its transport handle and callback generation are not discoverable from public status.

Replace the recovery meaning of `after` with explicit lifecycle facts: before tuple/input correlated; executor entered; executor Promise settled with fulfilled placeholder or exact locally-created stopped Error; parent after entered with exact correlation; parent after Promise settled. Retain the ordinary duplicate-result protection separately. A final `finally` inside the executor is not by itself proof that the returned executor Promise settled: observe its actual returned Promise. Do the same for the Promise returned by each owned hook body. Register its terminal reaction before exposing that Promise to the native adapter. No bookkeeping operation may remain queued after claiming settlement. Tests must exercise reentry both inside body finalization and between Promise reactions. This proves only this adapter's JavaScript work, not native hook delivery owned by other plugins.

For a successful executor return, normal exact placeholder correlation remains required. If a deadline/cancel stop occurs before its parent after, do not finalize/consume that candidate. For an error return, capture the exact private stopped Error generated for this invocation; accept a terminal callback fact only when the original before tuple and canonical input match, executor is settled rejected with that Error, native after has `status:"error"`, and its native wrapped error's `error` field is that same object. Other status/shape/payload, a lookalike error or a merely equal message disqualifies. Extend the local `V2ToolAfter` projection with the supported error field; preserve native error semantics. Do not fabricate a completed result for an error after-event. Keep error text fixed and bounded; do not attach child text or private objects to output/content/metadata. On completed after-events initialize all three channels to rejection before correlation, as today. No stopped parent return becomes accepted output.

Record child invocation identities at before entry and keep them until the matching after body and returned Promise settle. Keep mechanical completion separate from proof validity. `afterTool` currently deletes a command entry before validating exit/tree; this cannot become a false empty-set proof: record a sticky proof error and the command's settled-with-error fact, or retain the entry. Missing/ambiguous after never drains. New child tool execution after stop is denied; it cannot continue old work. A pre-stop command's known correlated after may settle in stopped state without granting its result acceptance. A stopped-state ledger lookup must not reuse `directRecord`, extend scope, or authorize tool execution.

Every owned callback entry/exit, command settlement, relevant event and disqualifier increments a managed recovery generation. Bind old callbacks to their retained task even after termination is proved; do not rely solely on `active` for their accounting. Unknown/mismatched late parent/child callbacks must still invalidate that retained attempt. Event loss/unload must disqualify *all unresolved direct records*, including ones with a prior after-event; the existing `if (!call.after)` filter is insufficient.

## Native reconciliation and deadlines

The author-selected recovery observation budget is 2,000 ms for the entire fresh sequence, using a separate monotonic deadline per explicit resolve/release observation. Production cannot receive this budget from model input. Test clocks may be injected through trusted test options. The original task deadline, budgets, gates and stopped status remain unchanged, even when reconciliation runs later.

Before starting, require the exact bound parent, same live plugin, registered owned handle/lease, allowed stop provenance, no sticky disqualifier, settled executor and correlated parent after, zero original/late native operations, zero owned callbacks/direct child pairs/pending commands, and complete create/event/prompt correlation. Publish the reconciliation reservation before any native call. Then perform serially:

1. Fresh `interrupt({sessionID: sealedChildID, resume:false})`; require fulfilled supported acknowledgment (either boolean value is valid, because wait supplies the idle proof).
2. `wait({sessionID: sealedChildID})` must fulfill after that interrupt.
3. `get({sessionID: sealedChildID})` must fulfill with exact child, original parent and implementer agent, present idle timestamp, and terminal outcome in `succeeded|failed|interrupted`.
4. `context({sessionID: sealedChildID})` must fulfill. Enforce the existing 256-message/1,048,576-byte post-allocation limits and unique nonempty IDs. Exactly one user message must have the sealed prompt ID and exact original text. Before it, allow only the existing initial agent/model/location switch entries. After it, allow only implementer assistant entries followed by a final idle entry; reject intervening switches, other users, unknown activity or wrong-agent assistants. Require final idle outcome to equal get outcome; failed/interrupted outcome is termination evidence only. A failed/interrupted run may have zero assistants; if present, assistants must have completed timestamps. Do not require successful result JSON/text/finish, consume its artifacts, or revive gates. Malformed shape, excessive context or unpromoted prompt blocks.

Check deadline, exact handle, authority and callback generation after every await. Track reconciliation operations just like original ones; its own expected operations advance the transport generation, while any unowned/old operation or callback change invalidates the observation. A timed-out reconciliation returns blocked while its pending operation stays recorded; it never issues the remaining sequence in a late continuation. Once that operation actually settles successfully, a later explicit resolve can start a wholly fresh sequence. A rejected operation or unexpected identity is sticky. No automatic replay, background retry, child deletion, inbox mutation, hidden provider request, or extension of the old deadline occurs.

Receipt fields are private: plugin/handle identity, exact original call/task/child/prompt/deadline binding, completed observation generation, callback generation at observation, terminal context digest and native outcome. None asserts semantic implementation success. There is no session lock or permanent fence against later trusted host activity; recheck native context before release and document this limitation.

## Controller, status and reviewed release ordering

Add a separate stopped direct record lookup; acceptance continues using `directRecord`. A normal-finalization `used` bit cannot destroy the recovery record, but any prior finalization fault remains disqualifying in this tranche. Keep an explicit state progression: stopped-awaiting-settlement, reconciling, termination-proved, ready-for-reviewed-release, released-fresh-only, with a sticky ineligible branch. Status names are diagnostics; private facts authorize transitions.

On the initial typed direct stop, retain baseline, allowed paths, run, attempt and lease, close candidate acceptance, clear original timers, and use existing controller interruption (`running/awaiting-guidance -> cancel-requested`). Capture the first recovery owner/ID/reason exactly once. Do not broadly change Job `recoveryFault` handling: private propagation of an already-known direct stop token is the only repeated-stop exception. Untyped interruptions still invalidate recovery. Keep controller capacity reserved until real termination proof.

`resolveRecovery` dispatches by the privately registered transport kind. Its direct branch never calls Job inspection or fabricates Job generation/output. After a receipt and authority rechecks, move only `cancel-requested -> cancelled` through existing `reconcileCancelled`; never mark succeeded/failed or release a gate. Retain the record as the direct recovery owner even if `active` is cleared, retain stopped state and the unresolved lease, and return the existing `state:"terminated"` shape. Repeated resolve must revalidate or replace the receipt, never infer proof from `cancelled` alone.

`recoveryStatus` remains callable by any eligible primary while stopped. Direct readiness requires an intact receipt/generation, bound authority and owned lease; an unknown lease without this in-memory capability remains blocked. It uses the original task `before` snapshot and original implementer allowed paths, checks the transition with `assertAllowedTransition`, and preserves the existing 32 changed-file review bound, tree hash, reason and nextAction fields. It does not call native reconciliation as a side effect, free capacity, or return private authority. A direct reason may distinguish pending operations, missing after, failed proof, unknown prior instance and review-ready. Existing Job status fields and behavior stay compatible.

Direct recovery must prove more than today's `verifySpec` marker-exists check: capture the exact start-marker bytes digest and device/inode at its original creation, normalized-spec digest and identity, canonical workspace/trace root and relevant parent directory identities in a direct-only authority record, before native create. Revalidate through bounded no-follow, before/after descriptor identity checks with existing ownership/mode/root rules. Do not derive a new baseline/identity after stopping. Check every retained run's existing spec authority, plus the direct attempt's captured stronger identity. Same-byte replacement or changed root/marker/spec/lease blocks. `assertClear(ownedLease)` already validates the exact private lease token, bytes and parent; it is not lease adoption or a general stopped exemption.

`releaseForFresh` retains its exact bound-parent and `expectedTreeHash` input, four-successful-recoveries-per-process cap and existing return shape. For direct:

1. Require ready status for that exact reviewed tree; hold a release/reconciliation lock before awaiting anything.
2. Perform another complete bounded native reconciliation, with the same drained ledger prerequisites. Require its context digest/identity to agree with the previous reviewed termination observation; new activity requires retained stop, not acceptance. Any failed/late/pending reconciliation blocks release.
3. After all awaits, synchronously recheck private receipt and both generations, original authority, every relevant spec/start marker, owned lease, original scoped transition and exact reviewed tree hash. No public tool callback or telemetry callback runs inside the final commit section.
4. Remove only the exact owned trace-wide unresolved lease using the existing synchronous checked lease API. Never remove `dispatch-started.json`, normalized spec or evidence. Consume the one-use receipt and retire the direct attempt after successful cleanup. Keep old call/task/child/prompt identities burned, add the task to terminal identity refusal, retain the old interrupted controller and discard any old candidate authorization.
5. Only after successful cleanup/retirement clear directUnresolved and the stopped recovery state, count the recovery and enable fresh admission. Emit diagnostics afterward. The old controller stays interrupted; a NEW orchestration/spec/task/call/child/prompt is required. Independent validators must establish gates again.

There must be no await between final receipt/tree/authority checks and lease cleanup/guard transition. This eliminates JavaScript scheduling gaps, not malicious same-UID replacement. A lease release error leaves in-memory stop closed and the receipt unusable for acceptance; report the exact affected absolute marker path and whether a checked file remains. Existing lease cleanup unlinks before post-unlink checks and can fail after removal: do not falsely claim the file was retained or promise crash-atomic recovery. Preserve the existing filesystem trust limitation; a stronger durable cleanup certificate is outside this tranche. Never advise manual deletion, changed trace roots, restart, opt-out or an older runtime as proof of release.

## Builder decisions and outstanding boundary

The builder may choose private type names and ledger storage details while preserving the interfaces' trust and lifecycle requirements. Error-object correlation, callback-Promise settlement ordering, all stop-origin propagation and lease cleanup ordering require independent review; if pinned native fixtures contradict any premise, reduce recoverability and retain refusal rather than substituting message equality or model confirmation. No owner product choice is currently unanswered. The explicit costs are narrow recovery eligibility, blocked cancellation without after, unchanged post-unlink/crash and same-UID limits, retained payload growth and no provider/live-host claim. Durable recovery, validator transport and compaction remain separately scoped later work.
