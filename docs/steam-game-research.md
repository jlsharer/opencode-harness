# Optional REA-assisted Steam-game research (WSL2/Linux)

This is a **project-only integration**, not authorization to inspect a game. Check the actual V2 `mcp.servers.rea` registration in `opencode.json` for its current enabled/disabled state; it may contain operator-specific, absolute launcher and provider paths. `docs/rea-mcp.example.json` is a **disabled, non-autoloaded** starting reference, not a replacement for project config. The example's `rea mcp` requires a separately verified, pinned, preinstalled executable on the OpenCode launch environment's PATH; it does not use `npx` or fetch a package. Verify the real registration, versions and provider readiness for each installation rather than assuming the example establishes them.

## Before enabling anything

1. Obtain authorization for the *specific* title and operation; check the EULA and applicable law. A Steam license alone does not grant all reverse-engineering rights. Start with a permitted offline, unprotected target. Stop at any DRM, anti-cheat, online/competitive, credential or legal boundary; never bypass protections, run or instrument protected games, extract secrets, patch or redistribute proprietary assets/binaries/decompiled code.
2. Check the actual selected OpenCode version/config dialect and all layered project/user config and environment-selected config paths. [V2 MCP](https://opencode.ai/v2/docs/mcp-servers/) uses `mcp.servers.rea` and `disabled: true`; [V1 MCP](https://docs.opencode.ai/docs/mcp-servers/) uses `mcp.rea` and `enabled`. Do **not** merge these dialects or copy the source guide's V1 `enabled: true` / numeric timeout into V2. A user/global registration may still be active even while this project registration is disabled. MCP connection state is distinct from tool permissions.
3. Consult the [REA released-package installation instructions](https://github.com/morluto/rea/blob/main/docs/installation.md), [REA client configuration](https://github.com/morluto/rea/blob/main/docs/client-configuration.md), [Ghidra releases](https://github.com/NationalSecurityAgency/ghidra/releases) and the selected Ghidra release's Getting Started/JDK requirements. Confirm the exact published `rea-agents` version, package provenance, Node/npm version support, native-provider compatibility and full 64-bit JDK **for those exact releases**. Do not assume the source guide's Node minima or Ghidra 12.1.x/JDK 21+ still apply. Verify `node --version`, `npm --version`, `java -version`, `javac -version`, `command -v ps`, and the executable/provider documentation. On WSL2 use Linux tools and paths (Windows PE support must be tested); set `GHIDRA_INSTALL_DIR` to the actual extracted folder, and `JAVA_HOME` to the matching JDK in the environment that launches OpenCode. A different terminal's exports do not carry over.
4. Only with owner approval, install a verified **pinned** package/provider outside this repository and review its outputs. If considering `rea setup --client opencode --skill=false --dry-run --json`, first check its installed-version help and inspect *all* proposed config/skill paths; it is not permission to run setup or mutate global config. Avoid `@latest`, implicit `npx -y` downloads, unreviewed installers and automatic setup. Run `rea doctor --provider ghidra --json` only after the chosen version is installed; doctor checks alone do not prove an active client connection. Provider processes may create caches even during static analysis.

## Explicit project activation (optional)

Do **not** merge the example or enable an entry merely because it appears in config. First confirm the selected client is V2, the registration launches a separately installed verified **pinned** REA release on a compatible Node version, and the matching Ghidra/JDK/provider environment is ready. Resolve launcher and provider paths from the actual operator environment; do not reuse another machine's absolute paths. After explicit owner approval, provider readiness and privacy review, enable only the intended project's `mcp.servers.rea` entry and fully quit/restart this harness's OpenCode launch. Preserve `$schema`, `instructions`, `permission.webfetch` and all other settings. Do not use REA setup as an alternative without checking which global/project files it writes. The harness launcher may reject colliding project configuration; this guide adds no portable/runtime dependency and does not enable REA in an external workspace.

Verify the loaded project config with `opencode mcp list` if supported by the selected client, then check the new client's REA tool catalog and scoped `binary_session {}`/`tool_availability` as documented by the installed REA release before requesting analysis. A doctor result, disabled registration or list entry is **not** proof of a connected provider or a completed analysis. Stop if startup, authorization, paths, versions or permissions are ambiguous. Teardown: set `opencode.json`'s project entry to `disabled: true`, restart this harness's client, and review separately installed provider caches and external research outputs before deletion; do not alter global settings blindly.

### Managed researcher access (V2)

This source project's `rea` registration uses `codemode: false` so native REA tool calls reach the managed V2 `execute.before` guard individually. A normalized work unit may carry `reaStaticInspection: { "path": "/absolute/target", "sha256": "<64 lowercase hex>", "tools": ["rea_inspect_pe_imports"] }` only when that exact target and operation were explicitly authorized. The bound researcher or validator may call `rea_inspect_pe_imports` with exactly `{ "path": "/absolute/target" }`. The guard checks lexical and no-symlink path identity, regular-file type, 64 MiB size limit and a streamed SHA-256 immediately before the call. A path mentioned only in a role packet, source constraint, or allowed workspace scope grants no REA access. Other MCP tools and other REA calls deny by default.

`inspect_pe_imports` works without an open REA binary session. `open_binary` and `close_binary` change REA session state, and deep target-affine calls may start a provider and write external caches, so managed roles cannot use them. Arbitrary-path REA tools, operations with execution, instrumentation, networking or writes, and names that merely sound read-only remain denied. A future deep-analysis workflow needs a separate target-affine identity and provider-effect policy; this static capability does not supply it. The hash check precedes the MCP call and cannot eliminate same-UID path replacement between check and provider open. Compare REA's returned Evidence hash and path before relying on the result. REA output is external evidence, never managed acceptance proof.

REA and Ghidra are external providers, not inside the managed Bubblewrap shell or Git-tree proof. Even an inspection tool can launch a provider, change REA's in-memory evidence/session state, cache data outside Git, and return untrusted target text. Do not interpret this allowlist as sandboxing, immutable target identity, legal authorization, or acceptance proof. Require independent target hash/provenance and addressable evidence before accepting findings; an MCP connection indicator by itself is not sufficient. Changes to the project MCP configuration or plugin code require a fresh client launch for this harness's operational verification.

## Bounded, reproducible static investigation

In WSL2, a default Windows Steam library may appear under `/mnt/c/Program Files (x86)/Steam/steamapps/common/`; other libraries may be under `/mnt/d/` etc. Quote spaces, confirm the mounted path and select the *actual* authorized binary rather than a launcher or protection module. Keep source and output apart: copy only the required authorized binary from Steam to a private research directory **outside this repository and Steam** (for example `$HOME/game-research/<title>/inputs/`), with separate `evidence/`, `notes/`, `reports/`. Do not edit the installed game; restrict access to copied proprietary inputs and keep them and analysis artifacts out of Git. Record game title/build, original path privately, selected file size, origin SHA-256 and staged-copy SHA-256 (`sha256sum`), and `file` type; require the two hashes to agree before analysis and recheck the copy afterward. Do not publish proprietary paths or content in reports.

Ask for **one specific feature**, static/read-only probes only: confirm REA and Ghidra session readiness and PE support, inspect metadata/imports/bounded strings, narrow to candidate functions through cross-references, then decompile only selected candidates. Limit tool output and calls; stop on huge output or provider errors rather than speculating. Every assertion needs binary hash/build, exact function or data address, tool operation/evidence identifier, assumptions and confidence. Check alternate explanations and, where lawful, clean offline observations or public docs. Decompiler pseudocode is an approximation, not source; client-side evidence cannot establish server-side behavior. Never request runtime instrumentation, game-service interaction, credential extraction, DRM/anti-cheat bypass or automatic modification.
