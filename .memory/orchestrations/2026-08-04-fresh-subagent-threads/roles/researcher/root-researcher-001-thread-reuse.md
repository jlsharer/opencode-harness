## Cited Findings

### 1. Native OpenCode already has the required fresh-versus-resume primitive

**Direct evidence.** Current OpenCode’s Task tool documents that each invocation starts fresh unless `task_id` is provided, in which case the same subagent session continues with its prior messages/tool output ([`task.txt:12-18`](https://github.com/anomalyco/opencode/blob/b8ea3ea091ea2b62b589d43af8b10e811195e39f/packages/opencode/src/tool/task.txt#L12-L18)). Its parameter schema says `task_id` is only for resuming a previous task ([`task.ts:43-52`](https://github.com/anomalyco/opencode/blob/b8ea3ea091ea2b62b589d43af8b10e811195e39f/packages/opencode/src/tool/task.ts#L43-L52)). Execution looks up `task_id`; without a resolved prior session it creates a child with `parentID`, agent, and derived permissions ([`task.ts:136-172`](https://github.com/anomalyco/opencode/blob/b8ea3ea091ea2b62b589d43af8b10e811195e39f/packages/opencode/src/tool/task.ts#L136-L172)). The task output exposes the selected child session ID as `task_id`/metadata ([`task.ts:181-213`](https://github.com/anomalyco/opencode/blob/b8ea3ea091ea2b62b589d43af8b10e811195e39f/packages/opencode/src/tool/task.ts#L181-L213), [`task.ts:330-357`](https://github.com/anomalyco/opencode/blob/b8ea3ea091ea2b62b589d43af8b10e811195e39f/packages/opencode/src/tool/task.ts#L330-L357)). Official agent docs also describe subagent work as child sessions and parent/child navigation (OpenCode Agents, “Usage,” fetched 2026-08-04).

**Implication.** Strict freshness is achievable by omitting `task_id`; deliberate same-thread continuation is achieved by supplying it. No custom session creator is necessary. A nonexistent/invalid `task_id` currently falls through to fresh creation (`task.ts:136-158`), so a policy test should reject any unauthorized presence of `task_id`, not merely compare resulting IDs.

### 2. The repository does not currently state or test a 1:1 task/thread rule

**Direct evidence.** Current orchestration surfaces require DAG decomposition, repeatable role instances, and unique scoped artifact IDs, but say nothing about child-session freshness or `task_id`: `.opencode/commands/delegate-orchestration.md:31-50`, `.opencode/skills/delegation-orchestrator/SKILL.md:25-34`, `.opencode/workflows/delegation-workflow.md:24-35`, and `.memory/protocols/memory-management.md:26-39`. The feature command similarly prefers narrow packets and repeatable instances but only limits “remediation loops” (`.opencode/commands/implement-feature.md:76-84`; `.opencode/workflows/implement-feature-workflow.md:57-71`). The role contract requires scoped inputs/outputs and trace paths but has no delegation-task, child-session, continuation-reason, or parent-session field (`.opencode/contracts/role-io-contracts.json:8-22`; schema permits only the catalog’s generic field lists at `.opencode/schemas/role-io-contracts.schema.json:30-68`). The trace schema’s `inputContract` is closed to three fields and likewise has no task/thread identity (`.opencode/schemas/memory-trace-artifact.schema.json:18-26`).

**Direct evidence on tests.** Source validation checks only recursive-document snippets such as DAG/research/planning/validation/remediation (`.opencode/scripts/validate-harness.mjs:653-688`) and command frontmatter (`:815-845`). Portable validation checks role/command shape and only the plugin `config` hook (`.opencode/scripts/validate-portable-harness.mjs:193-208,235-265`). Portable E2E tests installation, inventory, and filesystem safety, not task/session behavior (`.opencode/scripts/portable-harness.test.mjs:65-131` and remaining file). No repository search hit establishes fresh child/thread, `task_id`, or authorized continuation policy in current runtime surfaces; the only direct task reuse description is retained prior research (`.memory/orchestrations/2026-07-19-multi-local-model-routing/roles/researcher/runtime-researcher-002-parallel-context.md:34-53`).

**Conclusion.** Today the requested rule is absent, so orchestration relies on OpenCode’s default fresh behavior and model discretion about whether to pass a returned `task_id`.

### 3. Current remediation wording is ambiguous; under the requested strict behavior it should be a new delegated task/thread

**Direct evidence.** Memory calls remediation a loop “per scoped work unit” (`.memory/protocols/memory-management.md:39`), while the skill says to request remediation from the “responsible role instance” (`.opencode/skills/delegation-orchestrator/SKILL.md:32-34`) and the central command says each scoped work unit may have three remediation loops (`.opencode/commands/delegate-orchestration.md:48-50`). The feature workflow says the integrator should “request remediation” (`.opencode/workflows/implement-feature-workflow.md:43-45`) but does not define session reuse. Existing retained memory also commonly assigns new artifact IDs containing `remediation`, demonstrating that remediation can be represented as a distinct role task, although history is not portable runtime policy.

**Inference/recommendation.** A parent-issued correction after a child’s returned/final result adds new acceptance feedback and asks for additional work. It is therefore a **separate delegated task** even when it remains charged to the same scoped work unit’s remediation-loop counter. It should get a fresh child session and a new artifact ID, with links to the failed result and validator/reviewer findings. This interpretation best satisfies strict 1:1 task/thread and avoids hidden stale context.

The sole same-thread exception should be narrowly defined as: the child explicitly requests guidance/clarification while the exact delegated task remains unresolved; the parent sends only the answer/necessary context using that child’s `task_id`; role, scope/task key, allowed paths, goal, and acceptance criteria remain unchanged; no new deliverable or post-result correction is introduced. A scope change, follow-up, retry after failure, validator/reviewer remediation, additional deliverable, or second role assignment is a new task/new child.

### 4. Prompt policy can strongly guide behavior, but only a Task-hook guard can block unauthorized reuse

**Direct evidence.** Agent files set `mode: subagent`, and every role denies nested `task` use (examples: researcher `.opencode/agents/researcher.md:1-8`, implementer `.opencode/agents/implementer.md:1-6`, validator `.opencode/agents/validator.md:1-8`). Thus parent orchestration is the relevant Task dispatch boundary. Role-specific commands bind a role (for example `.opencode/commands/delegate-research.md:1-12`), while `/delegate-orchestration` and `/implement-feature` are parent-owned with `subtask: false` (`.opencode/commands/delegate-orchestration.md:1-8`; `.opencode/commands/implement-feature.md:1-8`). Official command docs say commands targeting subagents invoke a subtask by default and `subtask` controls that behavior (OpenCode Commands, “Agent”/“Subtask,” fetched 2026-08-04), but command templates do not expose an enforceable “never resume” setting.

**Direct evidence on hook capability.** Current plugin types expose `tool.execute.before(input {tool, sessionID, callID}, output {args})`, `tool.execute.after(..., output {title, output, metadata})`, `tool.definition`, and a generic event hook ([OpenCode plugin types `index.ts:222-281,331-335`](https://github.com/anomalyco/opencode/blob/b8ea3ea091ea2b62b589d43af8b10e811195e39f/packages/plugin/src/index.ts#L222-L281)). Session events include `session.created`, whose info contains `id` and optional `parentID` ([SDK generated types `types.gen.ts:533-567`](https://github.com/anomalyco/opencode/blob/b8ea3ea091ea2b62b589d43af8b10e811195e39f/packages/sdk/js/src/gen/types.gen.ts#L533-L567)); official plugin docs list `session.created/updated/idle/error` and before/after tool hooks (OpenCode Plugins, “Events,” fetched 2026-08-04).

**Enforceability conclusion.** A before-hook can block a Task call when `output.args.task_id` is present without a recorded one-shot same-task clarification authorization. An after-hook can observe child metadata/output and maintain an in-process audit ledger; `session.created` can corroborate parent-child creation. Prompt/docs/checklists and static validators can require the convention but cannot themselves stop a model from reusing `task_id`. Event-only telemetry cannot prevent the already-executed reuse.

### 5. The existing lifecycle hook does not currently provide that enforcement and contains payload/event mismatches

**Direct evidence.** `.opencode/plugins/index.js:1-8` is only an adapter merging lifecycle and routing hooks. `.opencode/plugin-modules/harness-lifecycle.js:7-21` listens for `session.start`, reads Bash arguments from `input.args`, and logs delegation only for Bash strings beginning `/delegate-` or routing scripts. Current OpenCode documents `session.created`, not `session.start`, and its hook type places pre-tool arguments in the second parameter `output.args`, not `input.args` (upstream citations above). It does not inspect `tool === "task"`, `task_id`, child metadata, role, or scope. Its `message.after` hook (`:22-26`) is not in the current upstream `Hooks` interface. Source validator merely checks separation/import and dynamic `config` reachability; it does not execute lifecycle event/tool behavior (`.opencode/scripts/validate-harness.mjs:704-746`).

**Conclusion.** Existing lifecycle behavior is, at best, prompt-adjacent telemetry; its destructive Bash guard and delegation notice appear ineffective against current typed payloads, and it cannot enforce fresh child sessions. This is a separate pre-existing defect relevant to any proposed guard implementation.

## Test Strategy

1. Pure guard tests: no `task_id` => allow fresh; any `task_id` without authorization => throw; explicit child clarification marker registers exactly one authorization; matching parent/child/role/scope + unchanged task contract => allow once; replay, wrong parent, wrong child, role/scope/path/goal change, follow-up, remediation, retry, and post-completion correction => reject.
2. Hook-shape tests: invoke `tool.execute.before(input, output)` and prove it reads `output.args`; invoke after-hook with Task metadata containing `sessionId`; feed `session.created` info with `parentID`; verify redaction/no raw prompts. Test multiple simultaneous children and no cross-session authorization leakage.
3. Prompt/static tests: require the same normative phrases/decision table across canonical protocol, skill, orchestration command, workflow, validation checklist, and portable seeds. Explicitly assert “remediation is a fresh child task” and “only child-requested same-scope clarification may reuse task_id.”
4. Manifest/bootstrap tests: update exact managed inventory and expected creation/unchanged counts; bootstrap into a foreign temp repo; ensure only portable files/minimal memory are required and orchestration history remains destination-owned.
5. Validator gates for the later validator role: `node .opencode/scripts/validate-harness.mjs`, the new lifecycle unit test, `node .opencode/scripts/portable-harness.test.mjs`, and installed-profile-equivalent `node .opencode/scripts/validate-portable-harness.mjs --root .`. 6. Operator-dependent live smoke test: dispatch two separately scoped tasks and confirm distinct child IDs; induce a child clarification request and confirm exactly one same-ID continuation; send remediation and confirm a new child ID. This is the only end-to-end proof of host behavior; offline hook fixtures remain guardrail evidence, not acceptance by themselves.

## Risks and Unresolved Questions

- A plugin’s process-local ledger is lost on restart. Decide whether post-restart continuation is always denied (strictest) or whether a redacted project-memory authorization record is allowed; persistent session IDs can be sensitive operational metadata.
- “Child-requested clarification” needs an unambiguous structured signal. Prompt text alone is forgeable/ambiguous; the repository has no native signed continuation token. A one-shot marker observed in Task output plus immutable scope matching is a guardrail, not a security boundary.
- OpenCode Task source does not validate that a supplied `task_id` belongs to the invoking parent or requested agent before reuse (`task.ts:136-172`). The harness guard should check its own recorded relationship; upstream behavior may change.
- Direct manual `@subagent` invocation and subagent-targeted slash commands may create child sessions without traversing a parent model’s Task hook in exactly the same way. Current docs establish child invocation, but repository/live testing is needed to determine whether strict policy covers those surfaces or must prohibit them for managed orchestration.
- Updating contract required fields can invalidate older retained traces if source QA later validates history structurally. Prefer versioning/optional migration or scope checks to newly created artifacts.
- The current lifecycle Bash guard mismatch should be corrected and regression-tested without expanding plugins beyond guardrail/telemetry status.
