# Operator-observed V2 native provider probe

- Provenance: external credential-free, filesystem-isolated live-provider fixture in a disposable project; not a managed validator gate or production harness launch. The selected Linux x64 glibc/AVX2 OpenCode binary was registry-integrity matched in the prior external verification and reported `opencode v2.1.4`.
- A disposable project plugin with a unique ID registered `context.tool.hook("execute.before", ...)` and wrote a private setup marker followed by a registration-complete marker. The V2 plugin API listed that ID after setup. Neither marker alone is proof of tool interception.
- The V2 CLI requested its native default `opencode/big-pickle` provider to invoke the built-in `general` subagent. The isolated server used an ephemeral API password, a disposable writable project, private temporary data/config/cache, a read-only host root and a sandbox-local DNS mapping; no provider credential, global config edit or production workspace plugin was supplied. The plugin wrote a rejection marker from its `subagent` before hook and threw `HARNESS_V2_FIXTURE_REFUSAL`.
- Observed client exit: `0`, with the refusal error in CLI output. Native session list: zero before, one parent after, zero sessions with a `parentID` after. This supports before-child rejection for this minimal disposable plugin in one live provider run; it does not prove production harness Task result handling, permission translation, cleanup, background cancellation or full V2 compatibility.
- A separate attempt using the existing V1 OpenAI OAuth access token as an OpenAI API key did not reach a tool call: the provider reported missing `api.responses.write` scope. No credential was copied into the worktree or written to this artifact. Direct provider DNS resolution failed inside the sandbox, so the successful credential-free default-model run used host-resolved address mapping only inside that sandbox with normal TLS hostname verification. No provider tokens, account identifiers, output text or private filesystem paths are retained here.
- On the same subsequent source tree, `node --test .opencode/scripts/native-v2-plugin-fixture.test.mts` and `npm test` exited zero. An operator-only external QA receipt (SHA-256 `3b0edf01ac7298fea1844ccd628e2e3c85c5c3386f68dc0f095e562e66f37e11`) records six exit-zero commands on unchanged HEAD/index/tree, with ignored `.opencode/.gitignore` bound; its tree SHA-256 is `e89528bad7ddb8c6864609396360852df10581628b2c743dd46ac952017ffbe6`. The receipt is external evidence, not a managed gate or proof of production V2 compatibility.
- Positive native control in the same disposable fixture: after explicitly permitting only the exact test `execute` call and its nested `subagent`, V2 observed `execute.before` with fields `tool, sessionID, agent, messageID, id, input` and `execute.after` with those fields plus `status, result`. The latter reported `status: completed`, `result` fields `output, content, metadata`, and metadata `sessionID, status`. Native session inventory changed from zero to one parent and one child with a parent ID; the child session ID matched the after-hook metadata. This demonstrates a completed subagent result and native child association for the fixture, not the production harness's typed packet, permissions or acceptance gates. One later parent-side tool was rejected by the fixture's deny-other-tools rule.
